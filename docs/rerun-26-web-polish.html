一、背景 内容落地了，前端还没跟上

第二十五批把仙界内容（秘境/功法/地点/丹药）补全了，但前端只靠行动按钮自动过滤——人仙玩家会看到「秘境·瑶池仙园」按钮，可这全靠 dungeon.is_locked() 自动过滤，没有「仙界身份感」，也没有结构化浏览入口：仙阶功法不会高亮，仙界秘境没有目录信息，飞升与否前端看不出来。

改动前：飞升玩家看到的是和凡人一摸一样的面板，只多几个「秘境·瑶池」按钮
改动后：「仙」金徽章 一眼认出来；功法「仙阶」金色高亮；秘境目录弹窗 结构化浏览（门槛/层数/冷却/奖励）
── 让「飞升不是终点」在前端也成立。

三、本批修的 bug 最值得警惕的一类

Bug · const 变量做 += 赋值 — 新增的秘境目录弹窗点击后 Toast「秘境目录加载失败」，但 fetch + json() + 数据全是好的（Node 模拟、浏览器分步验证都 200/5 条）。根因：openCatalog 里写了 const cls = c.state.indexOf(...) ? ... : ...; 然后 if (enterable) cls += c.is_immortal ? " immortal" : ""; —— 给 const 赋值抛 TypeError: Assignment to constant variable，被函数内 catch 吞掉 → 只 toast 不抛，检查无痕。改 let cls 解决。

排查手法：SPA 里「功能点了没反应 / 报错被吞」要怀疑 JS 语法级错误。用 agent-browser eval 分步复刻（fetch → json → map → render），定位到具体语句，而不是看 Toast 文案猜。

四、设计要点 为什么这么做

结构化端点优于解析文字流 —— 前端原本只能发 dungeon list 拿终端文字，渲染脆弱（依赖文案格式）。改为后端加 catalog_data() → /api/catalog 返回结构化 JSON，前端渲染卡片。文字流只用于叙事日志，不用于结构化内容。
复用服务端口径，单一事实源 —— 秘境「能否进入」服务端已有 dungeon.is_locked()（返回中文原因），catalog_data() 直接复用它取 state，前端只渲染不重复判断（门槛/锁定/冷却），两边口径不漂移。
