## 二、候选模块

### A. 装备系统（建议第一批）

**作用**：让物品真正改变战力，给战斗、渡劫、秘境提供成长载体。

**接入方式**
- `config/items.py`：`ItemDef` 增加 `equip_add: dict` 与 `equip_mul: dict` 两个字段（frozen dataclass，给默认值，不影响现有 12 件物品）
- 新增 `xiuxian/systems/equipment.py`：穿戴时 `attributes.add_modifier(Modifier(source=f"equip:{slot}", add=..., mul=...))`，卸下 `remove_modifier` 同 source
- `Cultivator` 增加 `equipment: dict[str, str]`（部位 → item_id），`to_dict` 写入、`from_dict` 用 `.get({}, ...)` 兜底
- 命令：`equip <物品id>` / `unequip <部位>` / `equip`（查看）

**为什么成本低**：属性注入完全走现有 Modifier，战斗、修炼、渡劫读的都是 `attributes.value()`，不需要任何适配。

**复杂度分档（待定）**
- 简版：6 个部位（兵器/护甲/法宝/靴/佩饰/腰带），纯属性加成
- 加强化：+N 强化等级，影响 add 值，需 `equipment` 存 `{item_id, level}`
- 加套装：同套装 N 件触发额外 Modifier，需在穿戴/卸下时重算套装

### B. 功法系统（建议第一批，与装备同批）

**作用**：给修炼速度和战斗风格提供可选择的成长路线，是「流派」的基础。

**接入方式**
- 新增 `config/arts.py`：功法表（id、名称、品阶、修习条件、加成 mul、熟练度上限）
- 与装备共用 Modifier 机制，但额外提供 `cultivation_speed` 类加成：修炼系统读取 `attributes.value("comprehension")` 已含加成，因此**无需改 cultivation.py 一行**
- 熟练度：订阅 `hour_passed`（修炼时累积）或 `combat_victory`（战斗累积）
- 命令：`art`（已修功法与熟练度）/ `art learn <id>` / `art switch <id>`

**与装备的关系**：同一套「挂载 → 注入 Modifier → 卸载」逻辑，两个系统一起做能共用代码，建议合并为一次实施。

**接入方式**（实际落地，详见文末第二批实施记录）

- 命令：`dan`（总览）/ `dan list` / `dan learn <id>` / `dan refine <id> [炉数]` / `dan gather [时辰]`

### D. 秘境探索（建议第三批）✅ 已完成

**作用**：中后期的主要内容消耗，把战斗、事件、掉落串成一条可反复刷的线。

**两种形态，工作量差约三倍**
- 线性层数推进（推荐）：每层抽一次「战斗 / 事件 / 宝箱 / 休息」，到底层给 Boss 与结算奖励。复用现有 `EventSystem` 的抽取逻辑与 `CombatSystem.fight`

### E. 功法主动技能（建议第五批）✅ 已完成

**作用**：把「灵力」这条线接活。此前功法只影响属性（被动加成），战斗仍是普攻 + 暴击，`p.mp` 在战斗中完全闲置——尽管配置一直在堆 `max_mp`（清心诀 +20、太虚养神功 ×1.30、大衍周天诀 ×1.12）。

**接入方式**：新增 `config/skills.py`（技能表）与 `systems/skill.py`（策略决策 + 扣蓝 + 计冷却），`ArtDef` 加 `skills: tuple[str, ...]` 字段，`CombatSystem` 在 `_player_strike` 里可选调用。

### F. 任务与声望（建议第四批）✅ 已完成

2. ~~**炼丹是否带失败率**~~ → 已定：**带失败率，不炸炉**（失败只损材料，退回一半）。
3. ~~**丹药是否分品阶**~~ → 已定：**分下品/中品/上品**，药效 70% / 100% / 140%。
4. ~~**秘境形态**~~ → 已定：**线性层数推进**。
5. ~~**老档兼容策略**~~ → 已定：新字段走 `.get()` 默认值，不升 `SAVE_VERSION`（实测老档照读，零迁移成本）。
6. ~~**技能施法模型**~~ → 已定：**自动施法 + 策略预设**（受 `fight()` 非交互契约约束，回合手动会废掉事件 / hunt / 秘境 / 推演四处调用方）。
7. ~~**仙界境界体系**~~ → 已定：**洪荒九阶仙**（人仙→地仙→天仙→玄仙→金仙→太乙→大罗→准圣→混元），与凡界九境对称，网文认知成本最低；飞升不是终点，法无止境。
8. ~~**仙界渡劫**~~ → 已定：**仙劫延续 + 分层名目**（仙劫 / 天衰之劫 / 道心劫 / 斩三尸 / 合道大劫，同一条判定只换文案参数）。
9. ~~**寿元机制**~~ → 已定：**取消死亡判定**（挂机养老定位，寿元纯展示），原 game.py 的寿元坐化逻辑移除。
10. ~~**挂机形态**~~ → 已定：**闭关命令 + 空回车打坐 + 离线收益**，三者收益与手动打坐完全一致（同一套 cultivate 逻辑，不做区分）；离线换算 1 现实小时 = 1 游戏日（可配），上限 24 现实小时；闭关不自动突破/不自动嗑药（决策点留玩家）。
11. ~~**产出/消耗口径**~~ → 已定：**一律按「本层需求比例」**，不挂境界序号指数派生量（第十二批教训：两者增速不匹配会导致比值崩塌）。
12. ~~**防刷模型**~~ → 已定：**精力预算（每天能主动操作多少）+ 时间预算（游戏时间流逝多快）双重约束**，修为速率上限被现实时间物理锁定。
13. ~~**加成聚合**~~ → 已定：**全局 BonusAggregator**——新增加成来源只需实现 `collect_bonuses(agg)` + 调 `rebuild_bonuses()`，核心零改动。
14. ~~**功法效果扩展**~~ → 已定：**声明式效果类型**（新增类型 = 声明 + 注册 + 消费端读一次），叠加规则按类型声明（attr_add 相加 / attr_mul 偏移相加 / 突破率取 max / 速率类相加且封顶）。

## 五、风险与取舍

- 装备若做套装，穿戴/卸下每次都要重算套装加成，注意用现有 `add_modifier` 的同名替换特性避免叠加 bug
- 功法若做熟练度，需决定是自动累积还是消耗资源修习，影响挂机收益曲线
- 炼丹若带炸炉，需要给玩家止损手段（保底符、品阶下限），否则容易劝退（本批选择不炸炉，已从根上规避）
- 所有新字段默认走 `.get()` 兜底，可在不升版本号的前提下保持老档可读

### 实施中发现并修正的问题

1. **事件总线的日志无处回收**：`bus.emit()` 不返回 handler 返回值，功法熟练度涨了但玩家看不到。改为订阅者把文本塞进 `payload["logs"]`，由广播方（`cultivate` / `_victory`）统一收回。
2. **渡劫失败不触发冷却**：渡劫未过走的是 `payload["blocked"]` 拦截分支，不经过 `_fail_penalty`，导致同一天可反复冲天劫（推演中实测连刷 4 次）。已在拦截分支补冷却。
3. **丹毒负反馈死循环**：无冷却时每天硬冲大境界，失败 +3 丹毒、每日仅消退 -1，越冲成功率越低。冷却是解法，不是调数值。
4. **灵石产出撑不起新消费出口**：战斗原本 `exp_reward / 20`，早期一场只掉 1 灵石，而最便宜的功法要 200。改为 `exp_reward / 10 + 8 × 难度系数`。
5. **`mult` 未在结算作用域内**：给掉落加装备时误用了 `spawn()` 的局部变量，改为在 `Enemy` 上存 `mult` 字段。

### 关键设计决策

1. **中品即基表**：`graded_id(x, "mid") == x`，下品/上品才带 `#low` / `#high` 后缀。这样老存档、掉落表、事件 JSON 里写的物品 id 一个都不用改，品阶机制对既有内容是零侵入的。
2. **品阶不手抄三份表**：`dataclasses.replace` + 效果缩放函数，加新丹药只要在 `GRADED_PILLS` 里添 id，三档自动派生，杜绝「改了中品忘了改上品」的失衡。
3. **成败与火候分工**：成功率看悟性气运，品质值看造诣与丹炉。若品阶只由归一余量决定，它必然均匀分布，造诣和丹炉就只剩「少废几炉」的意义了。零造诣无丹炉时三品各 1/3；满造诣配朱雀丹炉后下品近乎绝迹。
4. **不炸炉**：只损材料（退回一半，向下取整），不动装备/境界/气血。失败也给三成修为与 0.4 点造诣，避免「连废十炉、颗粒无收」的劝退。
5. **丹方可换购**：开局只会两张，其余用灵石买。既给后期灵石一个去处，也避免「高级丹只能靠随机事件」的死锁（原本灵草只有战斗 25% 掉落和个别事件，加了 `dan gather` 才让上游通了）。
6. **清毒丹**：上品药力 140% 但丹毒也 140%，清毒丹是这套负反馈的泄压阀。

### 实施中发现并修正的问题

1. **满级时战利修为是 inf**：`spawn()` 用 `p.exp_required()` 作基数，已至绝巅时它是 `inf`，`int(inf)` 直接抛 `OverflowError`（长线推演到渡劫后期必崩）。已改为退回上一层需求。
2. **灵石产出指数膨胀**：第一批把灵石写成 `exp_reward / 10`，而 `exp_reward` 随境界需求指数增长——渡劫期一场掉上亿灵石，把全部消费出口变成零头（推演结余 288 亿）。已改为只看境界序号与难度系数：`(8 + 6×难度) × 1.6^境界序号`，炼气约 14、渡劫约 600，推演结余降到 13 万。
3. **品阶标签重复显示**：背包里出现「上品·聚气丹 ……（上品，药力 140%）（可服用）（上品，药力 140%）」——品阶已写进名称与描述，面板无需再加标签。
4. **「丹毒 +-21」**：`poison` 效果原本按正值格式化，清毒丹传负值就打成了 `+-21`。已分正负两支。
5. **批量炼制的收尾文案**：材料不足时 `refine` 会「停火」且不推进时间，日志却仍按「共 N 炉」收尾，看不出开了几炉。已改为记录实际点火数。

### 关键设计决策

1. **难度锚点是 tier 不是层数** —— 敌人按玩家境界等比缩放，同 tier 的层打起来一样难，层数只是 tier 的载体。浅层 weak → 中层 normal → 深层 elite → 底层 boss。

5. **奖励走效果 DSL 且修为用 `exp_ratio`** —— 写固定修为在炼气期能直接飞升、到渡劫期等于零，和「灵石挂在指数增长量上」是同一类坑。

### 关键设计决策

1. **开局自动接取，不提供手动 accept** —— 玩家的目标感应来自「手头永远有活干」，而非要去任务板翻找。可用任务按 `min_realm` / `once` / 已接 / `min_rep` 过滤后自动进 `accepted`，目标达成即交付、可重复任务进度清零续接。

5. **买卖不耗时间** —— 与修炼/秘境/战斗的时序脱钩，坊市只是资源转换站，不会吃掉修炼节奏。

### 关键设计决策

1. **消耗与产出一律按比例，不写绝对值** —— 灵力上限跨五个数量级（开局 40 → 炼气 220 → 渡劫 1173 万），写 `mp_cost=20` 在炼气是 9% 的蓝条、到渡劫只剩 0.0002%，与「灵石挂指数」「秘境修为写固定值」是同一类坑。按比例后实测庚金一击在九个境界都恰好是蓝条 10.0%。
2. **自动施法 + 策略预设，不碰 `fight()` 契约** —— `fight(enemy) -> list[str]` 一次调用打完，调用方有四处：`effect_battle`（事件自动开战无处输入）、`hunt`、`dungeon.next()`、测试与推演脚本。决策权交给三档策略：保守（留 40% 蓝、55% 治疗线、70% 护体线）、均衡（20% / 35% / 45%）、激进（倾泻 / 25% / 不护体）。
3. **职责边界：技能系统只管「决策 + 付费 + 计时」** —— `choose_action` 返回计划（已缩放威力、已扣蓝），战斗系统持 enemy 负责结算伤害/治疗与写日志，两处不互相持有数据。
4. **回灵零耗是刻意的** —— 它是「灵力见底」死局的出口，代价是让掉一回合，必须恰好能在蓝空时放出来。
5. **冷却存 `cooldown + 1`** —— `next_round()` 先减 1 再判 0，配置写 `cooldown=2` 就真的压 2 回合（实测庚金一击在日志第 3 / 9 / 15 回合连发，间隔 6 = 每 3 回合一次）。
6. **两处「不浪费回合」的判定** —— 敌人残血（<20%）时任何策略都不放护体（减伤救不了人，多点输出才能结束战斗，否则保守档会护到打满 40 回合）；攻击技能全在冷却且八成药力会溢出时，满血不疗伤、满蓝不回灵，宁可普攻。
7. **可选装配的降级保证** —— 战斗侧只 `game.systems.get("skill")`，取不到就完全按原样普攻。卸掉技能系统，事件自动战斗、秘境推进、100 项既有测试与推演脚本行为分毫不变（专门有 `test_combat_unchanged_without_skill_system` 守着）。

### 实施中发现并修正的问题

1. **`fight()` 钩子 IndentationError** —— 插入技能钩子时缩进写错（模块级 4 空格接了函数体 8 空格），84 个测试连锁报错。重写整块为正确的 8/12 空格缩进后恢复。
2. **战后冷却残留** —— 冷却只在 `begin_battle` 清空，战后 `skill` 面板一直挂着「[冷却中 剩 N]」，看起来像永久失效。加 `end_battle()` 在战斗收尾清空（连 `_guard` 一并归零）。
3. **满血放疗伤白让回合** —— 冒烟测试发现攻击技能进冷却后，系统会在满血时放「清心咒」治疗 1 点血（日志「气血回复 1（60/60）」）。加 `_worth()` 判定：八成药力落不进去就宁可普攻。
4. **保守档打满 40 回合** —— 推演里 3.2% 的战斗超时未分胜负：残血还在放护体。加 `finishing_guard` 判定（敌人 <20% 血不放护体）后超时降到 ~1%（seed=2026：246 → 149；seed=7：18 → 9）。
5. **推演脚本自身两个坑**（非游戏 bug）—— 学功法门槛写成 4 万灵石导致全程零技能；`can_breakthrough()` 为真但精力不足 30 时原地空转。分别改为「按单价 2 倍门槛」与「精力 ≥30 才冲关」。

### 背景

### 关键设计决策

1. **文案与数值严格分离** —— 战斗日志的叙事部分（cast、词库、铭文）全部落在数据层/模块常量，换文风不碰 combat.py 的判定与结算逻辑一行。这是「文字即玩法」的落点。
2. **锚点词是契约** —— 普攻行含「你击中」、技能行含「施展【」、受击行含「反扑/受到/剩余」、胜利行含「倒地不起」。demo、推演脚本、自动化测试靠锚点辨认行为；`TestProse` 专门守着这套契约，文案随便改、锚点不许丢。
3. **词库消耗与判定同一个随机源** —— 文风抽取走 `game.rng`，同 seed 输出依旧完全可复现；代价是相对第五批的随机序列整体偏移（推演细节数字变化），但数值公式与判定规则零改动。
4. **未配置 cast 自动降级** —— 第三方/事件发放的功法没有 cast 字段时退回通用句式，战斗不受影响，与技能系统可选装配的降级哲学一致。

### 三条核心公式（全部可解释）

```
突破率 = 夹[5%, 98%]( base × (1 + 0.15%×(体质−10) + 0.10%×(悟性−10) + 0.05%×(气运−10))
                      − 0.015%×丹毒 + 丹药 + 神通·言出法随 )
```

旧式是加和（`base + 0.01×(体质−10) + ...`），体质 ≥18 即被 clamp 顶格到 98%，三维后期完全失效；比例式让三维按 base 等比例放大——大乘期（base 0.18）三维 500 时实际 0.45，后期依然可解释、有贡献。渡劫率本就是比例项（防御占气血比 + 神识/200 + 气运/100），未动。

```
修炼产出/时 = 6 × (1 + 悟性/50) × 灵气密度 × (1.6^min(境界序号,8)) × (3^max(0,境界序号−8))
              × (1 + 神通修炼加成) × 随机[0.88, 1.14]
```

凡界每境 ×1.6（原样），仙界灵气质变每境 ×3；金仙「仙域」再叠 +15%。

```
顿悟：每 4 时辰判定一次，概率 5% + 气运/1000，奖励 = 当前层需求 × (8% 凡界 / 12% 仙界)
```

### 本批踩的坑（重要）

1. **顿悟按打坐次数而非时长** —— 原实现每次 cultivate 只掷一次骰，挂机 `cultivate(24)` 一天 1 次判定 vs 手动 `cultivate(4)×6` 六次判定，**挂机收益只有手动 1/6**，与挂机养老定位直接冲突。改为每 4 时辰判定一次（`rolls = round(real_hours/4)`），挂机/手动收益一致。
2. **顿悟 inf 死循环** —— 混元圆满后 `exp_required()` 为 inf，顿悟 `bonus = inf×0.08 = inf`，`add_exp(inf)` 把修为污染成 inf → `can_breakthrough` 恒真 → 突破永远返回「已臻绝巅」且不推进时间 → 死循环（模拟进程 SIGTERM/137）。修复：顿悟前判 `exp_required() != inf`。
3. **模拟脚本被冲关冷却卡死** —— 突破被冷却拦截时返回提示但**不推进时间**，脚本若在 `can_breakthrough` 分支反复冲关会原地死循环。模拟循环必须显式 `rest` 熬冷却。这与 README 记忆里「凡是需要玩家交互才能继续的入口，推演脚本都要显式处理」是同一类坑。
4. **模拟脚本显示 bug** —— 打印突破率/渡劫率时用「最终状态」的玩家属性算，所有行都显示同一个值（26.1% 之类）。改为记录节点时快照当时的概率。

### 验证

- **141 项单元测试通过**（原 126 + 仙界/公式/挂机 15 项）
- demo.py（seed=42）跑通 4.12 飞升段：「霞光万道，天门洞开，渡劫后期 -> 人仙初期！你飞升仙界！」+ 铭文 + 仙体神通注入 + 面板显示，存档读档一致性通过
- 交互冒烟：地仙圆满→天仙真实链路显示「天衰之劫感应…渡劫成功率 73.1%」，渡劫成功 +5% bonus 后突破独立判定（30.0% = 0.11×2.27 + 0.05 数学自洽）

## 十三、第八批实施记录（闭关挂机 + 离线收益）

### 背景

用户指令：「打坐可以自动打坐，就算挂机了也一直打坐就行了，收益就不要区分了。」——挂机养老定位的进一步落地：打坐自动化、离线持续打坐、收益与手动完全一致（上一批「顿悟每 4 时辰判定」已统一手动/挂机收益，本批把打坐本身自动化）。

### 实际落地

| 文件 | 变更 |
|---|---|
| `core/cultivation.py` | 新增 `CultivationSystem.idle(days)`：闭关推演「打坐→精力耗尽→休息→继续」循环，**内部调用同一套 cultivate/rest**（收益天然一致，无任何额外加成）；修为圆满自动停（突破留给玩家）；无参闭关至修为满，单次上限 `IDLE_MAX_DAYS=30`；注册 `idle` 命令 |
| `factory.py` | 新增 `settle_offline(game, saved_at)` + `load_game` 接入：读档按真实流逝时间结算离线打坐（`OFFLINE_DAYS_PER_HOUR=1`，上限 `OFFLINE_MAX_HOURS=24`）；结算后立即重写存档刷新 `saved_at`，防重复结算 |
| `ui/cli.py` | 空回车 = `cultivate 4`（在线挂机连按回车即持续修炼）；help 面板加「回车」条目 |
| `demo.py` | 新增 4.13 闭关演示段（人仙闭关 3 日，展示自动循环） |
| `tests/test_core.py` | 新增 `TestIdleCultivation`（4 项：闭关天数/修为增长、修为满提前停、上限、不嗑药）与 `TestOfflineReward`（3 项：离线结算、不重复结算、即时读档无收益）；148 项全过 |

### 关键设计

1. **收益不区分是硬约束** —— 闭关/离线全部复用 `cultivate()` 本体（含顿悟、熟练度、地点密度、神通加成），没有独立的「挂机收益公式」；只有「循环调度」是新的（打坐→休息→打坐）。
2. **突破是决策点，不自动化** —— 闭关期间修为圆满即停，提示 `breakthrough`。理由：突破率、丹药、渡劫是玩家的决策时刻（含失败惩罚 -35%），全自动会剥夺决策且让失败惩罚变得「与我无关」。
3. **离线防重复结算** —— 结算后重写存档（saved_at 刷新为当前时刻），同一存档反复读档不产生第二次收益。测试守着。
4. **离线时间戳复用现有字段** —— `saved_at` 早已存在于存档 payload（`%Y-%m-%d %H:%M:%S` 字符串），零存档结构改动，老档照读（无此字段则跳过结算）。

### 本批踩的坑

1. **闭关「0 日」文案** —— 低需求境界（炼气 100 修为）一坐即满，闭关实际不足一日就停，日志却显示「闭关 0 日」。改为 `闭关不足一日`。
2. **离线防重复测试的舍入差** —— 结算后 `manager.save` 重写存档，`to_dict` 把修为舍入到两位小数，二次读档断言 `==` 失败（1194.9312 vs 1194.93）。改 `assertAlmostEqual(delta=0.01)`，日志为空已证明逻辑正确。

### 验证

- **148 项单元测试通过**（原 141 + 闭关 4 + 离线 3）
- 闭关冒烟：元婴需求 11 万，`idle 5` 闭关 5 日 +2432 修为、day 1→6；炼气 `idle 30` 修为满即停（不自动突破）
- 离线冒烟：存档时间戳拨回 2 小时 → 读档显示「离线归来：阔别 2.0 时辰（约 2 日）」+ 闭关日志 +18698 修为 + 顿悟 2 次；二次读档无结算
- demo 4.13 闭关段 + 存档一致性「通过」

## 十四、第八批（二）实施记录（现实时钟：在线 1.5 倍 / 离线 1 倍）

### 背景

用户追加指令：「优化一下吧，在线时间按 1.5 倍算，离线时间按 1 倍算……重点是全程要跟着现实时钟走。」——从「命令驱动 + 离线结算」升级为「全程现实时钟驱动」：开着终端挂着不动也一直打坐（在线倍率 1.5），关掉游戏读档结算（离线倍率 1.0）。

### 实际落地

| 文件 | 变更 |
|---|---|
| `core/cultivation.py` | `idle()` 支持小数天（float）：按游戏总小时精确推进（`day×24+hour`），打坐/休息时长都按剩余目标截断，不再 overshoot；日志「闭关 5.0 日」/「闭关 12 时辰」 |
| `factory.py` | 新增 `settle_realtime(game, seconds, days_per_hour)` 通用结算（在线/离线共用）；常量 `ONLINE_DAYS_PER_HOUR=1.5`、`OFFLINE_DAYS_PER_HOUR=1.0`、`CLOCK_MAX_HOURS=24`；`settle_offline` 重构为其特例；不足 1 游戏时辰不结算（防秒级噪音） |
| `ui/cli.py` | 主循环记录 `last_clock`，每次命令前 `_settle_online()` 结算命令间隙的现实时间（≥60 秒才结算）；日志头「时光流转 X 时辰（游戏内约 N 日）」 |
| `tests/test_core.py` | 新增 `TestRealtimeClock`（3 项：在线倍率 72 时辰精确、低阈值不结算、24 时上限）+ `TestIdleCultivation` 增 2 项（小数天 12 时辰、float 上限）；153 项全过 |

### 关键设计

1. **时间模型**：手动操作 → 命令推进；命令间隙 ≥1 分钟 → 现实时钟接管（在线结算）；关游戏 → 离线结算（读档时）。三条路径全部复用同一套 `idle -> cultivate`，收益天然一致。
2. **在线倍率 1.5 的设计含义**：鼓励玩家开着游戏（活跃），离线也不吃亏（1.0），放置游戏常见「在线加成」。
3. **结算粒度**：不足 1 游戏时辰不结算（在线约 2 分钟内无感，正常操作间隙零打扰）；`rest`/`cultivate` 时长按剩余目标截断，float 天结算不 overshoot。
4. **上限双保险**：`CLOCK_MAX_HOURS=24` 现实小时（防挂机一年满级）+ `IDLE_MAX_DAYS=30` 游戏日（idle 兜底）。

### 本批踩的坑

1. **rest(8) 固定时长 overshoot** —— 结算 72 时辰目标，精力耗尽时 rest(8) 会推进超过目标（实测 78 时）。改为 rest 时长按剩余目标截断。
2. **测试表达式 bug** —— `game.day + game.hour/24` 把「第 N 日」（从 1 起）当「N 天」累加，断言 3.0 日实际算出 3.25。应为 `(day-1)×24 + hour` 计算总小时差。

### 验证

- **153 项单元测试通过**（原 148 + 现实时钟 3 + 闭关小数 2）
- 调试验证：`settle_realtime(7200s, 1.5)` → 72 时辰精确推进（day 1→4 hour 6→6），修为 +10627、顿悟 1 次
- 交互冒烟：main.py 正常启动，空回车/命令间隙结算路径无异常

## 十五、第八批（三）实施记录（后台周天：并行被动修炼）

### 背景

用户指令：「可以后台自动挂机吗？就是进行其他操作，不影响打坐。」——做战斗/秘境/赶路/炼丹等其他操作时，打坐收益照拿，互不影响。落地为**被动修炼（后台周天运转）**：任何时间推进自动涨修为，不占精力、不打断操作。

### 实际落地

| 文件 | 变更 |
|---|---|
| `core/cultivation.py` | 抽取 `_hourly_gain(p, rng=None)` 公共产出函数（主动传 rng 有随机、被动取期望）；新增 `on_bind` 订阅 `hour_passed` → `_on_hour_passed` 被动结算（产出 × `PASSIVE_RATIO=0.6`，静默不产生日志）；`cultivate` 主动打坐期间置 `_active_meditating` 标记暂停被动（防 1.6 倍双叠加） |
| `tests/test_core.py` | 新增 `TestPassiveCultivation`（4 项：赶路涨修为不耗精力、被动<主动且 ≥0.53 倍、主动无叠加、休息也涨）；修正 `test_breakthrough_success_advances_stage`（突破耗时 2 时被动周天会进账少量修为，不再是精确 0）；157 项全过 |

### 关键设计

1. **并行不互斥**：被动修炼挂在全局 `hour_passed` 上——战斗、秘境、赶路、炼丹、休息任何时间推进都带被动修为，与操作并行，不占精力、不打断。
2. **主动打坐仍是高收益路径**：被动只有 60%（无顿悟、无功法熟练度），主动打坐 100% + 顿悟 + 熟练度——前期打坐是主力，后期顿悟拉开差距，被动只是「顺便练」。
3. **防双倍叠加**：`cultivate`/`idle` 主动修炼期间 advance_time 也会广播 hour_passed，用 `_active_meditating` 标记跳过，避免主动+被动 1.6 倍。
4. **静默结算**：被动修为不产生日志（战斗/秘境每层都要推进时间，刷屏会淹没操作反馈），从面板修为数字可见。
5. **无漏洞**：休息也涨被动（rest 8 时 = 8×60% 无顿悟，效率不如主动打坐，rest 刷修为无利可图）。

### 验证

- **157 项单元测试通过**（原 153 + 被动修炼 4）
- 端到端：连续 3 场战斗，每场后台周天 +15~17 修为、战斗正常（精力 100→25）、无打断；赶路 6 时 +39.4 修为不耗精力 vs 主动打坐 6 时 +60.6（60% 比例成立）
- demo 全流程 + 存档一致性「通过」

## 十六、第九批实施记录（数值防膨胀：大数格式化 + 平衡收口）

## 第二十七批：仙界深度重构（法则 / 仙门 / 仙界事件）

### 背景与诊断

承接第二十六批遗留的「仙界第二片空白」。先跑 `scripts/simulate_realms.py` 取实测数据定位痛点：

| 指标 | 实测 | 问题 |
|---|---|---|
| 凡界九境 | 669 天（**74 天/境**） | — |
| 仙界九境 | 592 天（**74 天/境**） | **与凡界完全同速**，飞升无体感差异 |
| 混元之后 | 1739 天无内容 | 终局空虚 |

**根因**（数学层面，非拍脑袋）：产出挂「本层需求比例」⇒ 每层所需时辰 = 需求 ÷(需求×0.002×密度) = 1/(0.002×密度) ≈ **常数**。仙界密度↑（4.5~6.0）恰好被 exp_growth↑（2.2~3.0）抵消。

**结论**：硬拉 `exp_growth` 无用（会被比例产出自动抵消）。必须**加第二条成长轴**。

### 需求确认

用户三连选择（AskUserQuestion）：

- 方向：**仙界法则系统 + 仙阶门派 + 仙界专属事件**（三块全做）
- 节奏：**深度重构仙界成长曲线**
- 数值：仙界总时长 **约 1170 天** / 法则 **分维度 + 预算限制** / 门槛 **软门槛（不达标则成功率大降，不禁突破）**
